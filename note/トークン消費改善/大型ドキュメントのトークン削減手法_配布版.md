# 大型ドキュメントのトークン削減手法（実践チェックリスト）

Claude Code などのAIコーディング環境で、
「マスター用のmdファイルが肥大化して、参照するたびにトークンを大量消費する」
——この状態を解消するための整理術をまとめました。

記事本文の要点を、作業しながら手元で見返せるチェックリスト形式にしてあります。
そのまま自分のプロジェクトに当てはめて使ってください。

配布：AI時短ラボ（ピクト）
自由に利用・改変して構いません。再配布は本ファイルのままでお願いします。

---

## 0. まず「困っているか」を確認する（分割の判断チェックリスト）

次のうち2つ以上当てはまるなら、分割の効果が大きい。

- [ ] そのファイルを1回読むだけで数万トークンを消費している（目安：1,000〜1,500行以上）
- [ ] 「今回の用件では読む必要がない部分」が、ファイルの半分以上を占めている
- [ ] 更新頻度が明らかに違う内容が同居している（毎日書き換える部分と、ほぼ変わらない部分が同じファイル）
- [ ] 「ちょっと状況を確認したいだけ」でも、毎回そのファイルの全文を読ませている
- [ ] ファイルが大きくて、1回の編集ミスで全体の整合性が壊れるのが怖い

> 当てはまらない小〜中規模のファイルは、無理に分割しない。
> 分割にも「ファイル数が増える」「参照が複雑になる」コストがある。
> **肥大化して実際に困ってから分割する** くらいでちょうどいい。

---

## 1. 問題の本質（なぜトークンを食うのか）

- `@ファイル名` で指定したファイルは、要約ではなく **全文** が読み込まれる
- 知りたい情報が数行でも、読まされる分量はファイル全体
- 「よく変わる部分」と「めったに変わらない部分」が混在していると、
  軽い更新のためだけに全体を読み書きする羽目になる

→ 対策は **「最初に読むもの」を極小化し、「詳細が要るときだけ開くもの」を分離する** こと。

---

## 2. 分割の3つの軸

厚い1ファイルを、次の軸で「薄いインデックス + 複数の専門ファイル」に割る。

| 軸 | 見分け方 | インデックス側 / topicファイル側 |
|---|---|---|
| **更新頻度** | よく変わる vs 安定している | 進捗・要対応リスト → インデックス／ルール・付録 → topic |
| **粒度** | 全体像 vs 個別の詳細 | 要点・ナビ → インデックス／1件ずつの詳細 → topic |
| **時系列・カテゴリ** | かたまりで分けられるか | 番号やカテゴリのまとまりごとに topic ファイルへ |

### 分割後の構成イメージ

```
マスター_YYMMDD.md   ← 数百行。共通ルール・要対応リスト・直近の進捗だけ。通常はこれだけ読む
topic_A.md           ← 個別の詳細（まとまり1）
topic_B.md           ← 個別の詳細（まとまり2）
...
ルール・付録.md       ← めったに変わらない参照情報
```

**効果の目安**：数千行の単一ファイル → 数百行のインデックスで通常作業が完結。
典型的な参照コストが約9割減。

---

## 3. インデックスに「残すもの / 逃がすもの」の仕分けリスト

### インデックスに残す

- [ ] ファイル構成の一覧表（どこに何があるか）＋ナビゲーション
- [ ] 全体共通のルール（頻繁に参照されるが、短くまとまるもの）
- [ ] 要対応リスト（最も参照・更新頻度が高い。分散すると探すコストが増えるので、あえて集約）
- [ ] 直近の進捗ログ（最新の数件だけ。古いものは圧縮・要約して残す）

### topicファイルに逃がす

- [ ] 個別の詳細（1件あたりの情報量が多く、同時に1件しか見ないもの）
- [ ] 安定した参照ルール・手順書（変更頻度が低く、読むタイミングが限定的）
- [ ] 過去の記録・経緯（読み返す頻度が低い）

---

## 4. 分割作業そのものを、AIに全文を読ませずにやる（grep → sed → wc -l）

ファイルを分割する作業でAIに全文を読ませたら本末転倒。
以下は「分割対象の内容を一度もモデルの文脈に載せずに」分割する手順。

- [ ] **① 見出しと行番号だけ取得する**
  ```bash
  grep -n "^#\{1,2\} " マスター.md
  ```
  本文は読まない。見出しの数はせいぜい数十行なので、AIに渡す情報量が激減する。

- [ ] **② 行番号から各セクションの範囲（開始行〜終了行）を計算する**

- [ ] **③ sed で範囲だけを新ファイルに書き出す**
  ```bash
  sed -n '89,1089p' マスター.md > topic_A.md
  ```
  Bashコマンドなので、内容はモデルの文脈を通らない。セクションの数だけ繰り返す。

- [ ] **④ wc -l で行数の整合性を検算する**
  ```bash
  wc -l マスター.md topic_A.md topic_B.md ルール・付録.md
  ```
  境界がずれて欠落があれば、合計行数が減るのですぐ気づける。

- [ ] **⑤ 新しいインデックスだけは自分の手で書き直す**
  要約とナビゲーションの追加が必要。ここだけは内容を扱うが、軽い作業で済む。

---

## 5. 分割してからの運用ルール（4か条）

- [ ] **通常はインデックスだけ読む。**
  特定の詳細が必要になったときだけ、該当する topic ファイルを開く。

- [ ] **更新時も同じ。**
  更新箇所がどのファイルに属するか先に判断し、そのファイルだけ
  `Grep` → `Read`（範囲指定）→ `Edit` する。全ファイルを読み直さない。

- [ ] **topicファイルを新しく作ったら、必ずインデックスの一覧表も更新する。**
  索引は放っておくとすぐ古くなる。

- [ ] **同じ内容を2箇所に書かない。**
  インデックスと topic で情報が重複すると、片方だけ直して不整合になる。
  インデックス側は「要約・リンク」に徹し、詳細は1箇所（topic）だけに置く。

---

## 6. よくあるケース別のヒント

- **詳細ファイルが最初から個別に存在している場合**
  新規に topic を作る必要はない。インデックス側の重複コンテンツを削除して、
  リンクに置き換えるだけで完了する（作業の主体は「再配置」ではなく「削除」）。

- **どこにも書いていない進捗ステータスがある場合**
  それは新規情報なので、迷わずインデックス側に残す。

- **1ファイルの分割で行数が合わない場合**
  セクションの境界（sed の行番号）が1行ずれていることが多い。
  `wc -l` の合計差ぶんだけ、範囲指定を見直す。

---

## まとめ

やることは2つだけ。

1. 「困っている」とそのままAIに相談し、**更新頻度・粒度・時系列でファイルを分ける設計**をもらう
2. 分割作業自体は、**Bash（grep・sed・wc）でAIに全文を読ませずに**実行する

「AIにたくさん読ませれば賢く動く」は誤解。
**AIに何を読ませないかを設計すること** が、快適なAIコーディング環境をつくる近道。
