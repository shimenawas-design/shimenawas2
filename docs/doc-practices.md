# ドキュメントのトークン消費を抑える方法

複数の文書にまたがるプロジェクトで、セッション開始のたびに全文書を読み込んでトークンを浪費するのを防ぐための手法。特定のプロジェクトに依存しない一般的な方法として書く。実例は末尾の「事例」を参照。

---

## 診断：原因は「文書が大きい」ではなく「重複」であることが多い

体感で「重そう」と判断せず、まず実測する。

```bash
# 各ファイルの文字数
for f in docs/**/*.md; do echo "$(wc -m < "$f") $f"; done | sort -rn

# 同じ内容が複数ファイルに散らばっていないか（特徴的な一文で検索）
grep -rl "特徴的な一文" docs/
```

よくある原因は、個々のファイルが大きいことではなく、**同じ情報が更新のたびに新しいファイルへコピーされ続けること**。日付付きの引継ぎ文書を作るたびに有効な情報を丸ごと転記していると、個々の判断は妥当でも積み重なって全文書が重複だらけになる。

---

## 対処：内容を役割で3種類に分ける

ファイルを「軽い/重い」で分けるのではなく、**役割**で分ける。1つの情報は1つのファイルにしか置かない。

### ① 索引
内容を持たない。**「何をしたいならどのファイルを開くか」の表**と、現況の要約だけを置く。自動で読み込まれる設定ファイル（例：`CLAUDE.md`）がある場合はそこに置く。ここが重いと毎回コストがかかるので、目安3,000字程度に収める。

```markdown
| やること | 開くファイル |
|---|---|
| 今の状態を知る | project/status.md ← 軽量・現状のみ |
| 共通ルールを確認する | common/policy.md |
| 経緯を追う | project/changelog.md ← 普段は不要 |
```

### ② 現状
**今どうなっているか**だけを書く。テーブル中心。「なぜそうなったか」は書かない。目安2,000〜3,000字。

### ③ 経緯
**なぜそうなったか・何を試して何が失敗したか**を書く。判断が必要なときだけ読む。長くなってよい。

複数プロジェクト・複数文書で共通の内容（規約、環境、外部仕様など）は、個々の文書に書かず**共通ファイル1本**にまとめる。共通ファイルが複数の文書から参照されている状態が正しい形。

---

## 古い文書は削除せず退避する

情報が古くなっても消さない。`archive/` のような場所に移し、通常の索引からは外す。理由を追いたいときだけ掘れるようにする。

```
docs/project/
├── status.md          今の状態
├── changelog.md        経緯
└── archive/
    └── snapshot-2026-08-22.md
```

---

## 日付付きファイルは「スナップショット」であって「更新履歴」ではない

日付付きファイル（引継ぎメモ・レビュー記録など）を新しく作るたびに、有効な情報を全部コピーする運用は破綻する。**生きている情報は「現状・経緯」の文書に一本化し、日付付きファイルは「その時点の記録」として以後編集しない。**

- 生きている文書（随時上書き）：現状・経緯・共通ルールの文書
- スナップショット（作成時点で固定）：日付が入った記録文書

新しい情報が確定したら生きている文書を更新し、古いスナップショットは退避する。

---

## リンクは相互参照で繋ぐ。内容は複製しない

「詳しくはこちら」で済む情報を、要約という体裁で本文に混ぜない。

```markdown
### 詳細
**[別ファイル](./other.md) を参照**（唯一の正）。
```

ファイル移動・リネームのたびにリンク切れが起きるので、機械的に検査する。

```bash
python3 - <<'PY'
import os, re, glob
for f in glob.glob("**/*.md", recursive=True):
    for m in re.finditer(r'\[[^\]]+\]\((\.{1,2}/[^)]+\.md)\)', open(f,encoding="utf-8").read()):
        t = os.path.normpath(os.path.join(os.path.dirname(f), m.group(1)))
        if not os.path.exists(t):
            print(f"✗ {f} → {m.group(1)}")
PY
```

**この検査は再構成した直後だけでなく、他セッションの変更を取り込んだ（pull・merge した）直後にも必ず走らせる。** 理由は次の項目。

---

## 複数セッションが並行編集する場合

ローカルとリモートなど、複数のセッションが同じ文書群を触る環境では、**互いに知らないまま独立に同じ整理をして衝突することがある**。

- push前に必ず fetch して、相手が同じファイルを触っていないか確認する
- コンフリクトが起きたら、**内容が新しく・裏付けが強い方**を採用する。両方の断片を無理に混ぜようとしない
- **マージが「クリーンに完了」しても安心しない。** 片方が古い前提で書いた大きな書き換えが、もう片方の直したリンクや表記を静かに巻き戻すことがある。マージ直後に必ずリンク検査を走らせ、内容も要所を読み直す

---

## 事例：Level Trim / Ongaku Toshokan（2026-08-24）

上記の方法を適用した実際のリポジトリでの結果。

**診断で分かったこと**：Sunoプロンプトが4ファイル、リリースカレンダーが4ファイル、規約・配信先判定が3ファイルに重複していた。原因は個々のファイルサイズではなく重複そのもの。

**対処**：共通ルールを `docs/policy.md` に一本化。各プロジェクトに `master.md`（現状）と `changelog.md`（経緯）を用意。古い引継ぎ文書は `archive/` へ。`CLAUDE.md` を内容を持たない索引に変更。

**効果**：

| | 再構成前 | 再構成後 |
|---|---|---|
| 全文書読み込み | 約89,000字（≈45,000トークン） | 約56,000字（archive除く36,000字） |
| セッション開始時に読む量（索引＋各現状文書のみ） | 該当なし（索引が無かった） | 約8,000字 |

索引を用意したことで、「今の状態を知る」だけなら全体の1/7で済むようになった。

**並行編集の衝突も実際に発生した**：この再構成の直後、ローカル環境の別セッションが独立に同じ整理（`master.md`のスリム化）を行っており、push が一度リジェクトされた。マージ自体はコンフリクトなく完了したが、その裏でローカル側の古い書き換えが、直したはずのリンクをローカル限定のファイル名に巻き戻していた。マージ直後にリンク検査を走らせて発覚し、再修正した。「クリーンにマージできた」は「正しくマージできた」の証明にならない、という実例。
