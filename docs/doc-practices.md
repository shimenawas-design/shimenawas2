# ドキュメントのトークン消費を抑える方法

**このリポジトリで実際に効果があった手法。** 2026-08-24の再構成（45,000トークン→8,000トークン）を題材にした具体的な手順。

---

## 原因は「文書が大きい」ではなく「同じ内容が複数箇所にある」

再構成前に実測したところ、原因は個々のファイルのサイズではなく**重複**だった。

| 内容 | 重複していたファイル数 |
|---|---|
| Sunoプロンプト全曲 | 4ファイル |
| リリースカレンダー | 4ファイル |
| 配信先・規約の判定 | 3ファイル |

`handoff-*.md` を書くたびに、まだ有効な情報を新しいファイルへ丸ごとコピーしていたのが原因。個々の判断は妥当でも、積み重なると全文書を読まないと状況を把握できなくなる。

**先に文字数を測ってから対処すること。** 体感で「重そう」と判断せず、`wc -m` で実測し、`grep -rl "特徴的な一文"` で同じ内容がどのファイルに散らばっているかを機械的に洗い出す。

```bash
# サイズの実測
for f in docs/**/*.md; do echo "$(wc -m < "$f") $f"; done | sort -rn

# 重複の検出（他のファイルにも同じ文が出ていないか）
grep -rl "特徴的な一文" docs/
```

---

## 対処：3種類の役割に分ける

ファイルを「軽い/重い」で分けるのではなく、**役割**で分ける。1つの情報は1つのファイルにしか置かない。

### ① 索引（CLAUDE.md）
内容を持たない。**「何をしたいならどのファイルを開くか」の表**と、今の状態の要約だけを置く。CLAUDE.mdは自動で読み込まれるので、ここを重くすると常にコストがかかる。目安3,000字。

```markdown
| やること | 開くファイル |
|---|---|
| 今の状態を知る | docs/x/master.md ← 軽量・現状のみ |
| 規約を確認する | docs/policy.md ← 共通 |
| 経緯を追う | docs/x/changelog.md ← 普段は不要 |
```

### ② 現状（master.md）
**今どうなっているか**だけを書く。テーブル中心。「なぜそうなったか」は書かない。目安2,000〜3,000字。

### ③ 経緯（changelog.md）
**なぜそうなったか・何を試して何が失敗したか**を書く。判断が必要なときだけ読む。長くなってよい。

複数プロジェクトで共通の内容（規約・配信先判定・環境の変化など）は、プロジェクトごとのファイルに書かず、**共通ファイル1本**（`docs/policy.md`）にまとめる。

---

## 古い文書は消さずに `archive/` へ

情報が古くなっても削除しない。`docs/<プロジェクト>/archive/` に移し、通常の索引からは外す。理由を追いたいときだけ掘れるようにする。

```
docs/level-trim/
├── master.md          今の状態
├── changelog.md        経緯
├── prompts.md          プロンプト（唯一の正）
├── review-2026-08-24.md
└── archive/
    ├── handoff-2026-08-22.md
    └── handoff-2026-08-23.md
```

---

## 日付付きファイルは「スナップショット」であって「更新履歴」ではない

`handoff-YYYY-MM-DD.md` を新しく作るたびに、有効な情報を全部コピーする運用は破綻する。**生きている情報は`master.md`等の「生きている文書」に一本化し、日付付きファイルは「その時点の記録」としてのみ残す。**

- 生きている文書（随時上書き）：`master.md` `changelog.md` `prompts.md` `policy.md`
- スナップショット（作成時点で固定、以後編集しない）：`handoff-YYYY-MM-DD.md` `review-YYYY-MM-DD.md`

新しい情報が確定したら、生きている文書を更新し、古いスナップショットは`archive/`へ。

---

## リンクは相互参照で繋ぐ。内容は繋がない

「詳しくはこちら」で済ませられる情報を、要約という体裁で本文に混ぜない。

```markdown
### Suno スタイル欄・据え置く語／動かす語
**[prompts.md](./prompts.md) を参照**（唯一の正）。
```

**ファイル移動・リネームのたびにリンク切れが起きるので、機械的に検査する。**

```bash
python3 - <<'PY'
import os, re, glob
for f in glob.glob("**/*.md", recursive=True):
    for m in re.finditer(r'\[[^\]]+\]\((\.{1,2}/[^)]+\.md)\)', open(f,encoding="utf-8").read()):
        t = os.path.normpath(os.path.join(os.path.dirname(f), m.group(1)))
        if not os.path.exists(t):
            print(f"✗ {f} → {m.group(1)}")
PY
```

## 複数セッションが並行編集する場合

ローカルとリモートなど、複数のセッションが同じリポジトリを触るなら、**独立に同じ整理をしてコンフリクトすることがある**（実際に本セッションで発生した）。

- push前に必ず fetch して、相手が同じファイルを触っていないか確認する
- コンフリクトしたら、**内容が新しい方・一次情報で検証されている方**を採用する。マージで両方の断片を残そうとしない
- 統合後は上記のリンク切れ検査を必ず走らせる（片方のセッションの命名規則が反映されていないリンクが残りやすい）

## 効果の実測（2026-08-24, Level Trim / Ongaku Toshokan）

| | 再構成前 | 再構成後 |
|---|---|---|
| 全文書読み込み | 約89,000字（≈45,000トークン） | 約56,000字（archive除く36,000字） |
| セッション開始時に読む量（CLAUDE.md + 各masterのみ） | 該当なし（索引が無かった） | 約8,000字 |

索引を用意したことで、**「今の状態を知る」だけなら全体の1/7で済む**ようになった。
