# タイトル案（3パターン）

1. **「manifest.jsonが見つかりません」← ZIPを普通に配っただけなのに起きた2つの罠**
2. **ZIP配布、これだけで詰みかけた。フォルダの二重入れ子と文字化けの話**
3. **非エンジニアにツールを配る時、ZIPの中身をフォルダで包んではいけない理由**

---

自作のChrome拡張機能を、身近な人に使ってもらおうと思ったことはありますか？

Chromeウェブストアを通さずに配る場合、「ZIPファイルを渡して、`chrome://extensions`から読み込んでもらう」という方法を取ることになります。手順は簡単なはずでした。

- ZIPを展開する
- 「デベロッパーモード」をON
- 「パッケージ化されていない拡張機能を読み込む」でフォルダを選ぶ

……のはずが、実際に使ってもらったところ、想定していなかった場所で2連続でつまずかれてしまいました。今日はその顛末と原因、直し方の話です。

---

## つまずき①：「manifest.jsonが見つかりません」

ZIPを展開してもらい、フォルダを選んでもらったところ、Chromeの「拡張機能を読み込む」ダイアログでこんな状態に。

- 背景で開いていたエクスプローラーには、`manifest.json`や`background.js`などのファイルがちゃんと見えている
- なのに、Chromeのフォルダ選択ダイアログでは、なぜか「icons」フォルダしか表示されない

[スクショ挿入箇所：Chromeのフォルダ選択ダイアログに「icons」しか表示されていない画面]

「ファイルが消えた？」「壊れてる？」と混乱させてしまったのですが、原因はもっと単純なところにありました。

### 原因：Windowsの「すべて展開」とZIPの構造が"二重"に噛み合っていた

配布していたZIPの中身は、こういう構造にしていました。

```
gemini-image-bulk-downloader-v1.0.0.zip
└── gemini-image-bulk-downloader/     ← ZIPの中で、さらにフォルダに包んでいた
    ├── manifest.json
    ├── background.js
    └── ...
```

一方、Windowsの「すべて展開」機能は、**ZIPファイル名と同じ名前のフォルダを自動的に新規作成**してから、その中に展開します。

つまり、ZIP側にも同じような名前のフォルダが入っていると、

```
（Windowsが自動作成したフォルダ）gemini-image-bulk-downloader-v1.0.0/
└── （ZIPの中に入っていたフォルダ）gemini-image-bulk-downloader/
    ├── manifest.json
    └── ...
```

という**二重の入れ子**が出来上がってしまうのです。

相手は当然、外側のフォルダ（1階層目）をChromeに選んでもらうわけですが、そこには`manifest.json`はまだ無く、`gemini-image-bulk-downloader`というフォルダが1つあるだけ——さらにその中に潜らないと目的のファイルに辿り着けません。

Chromeの「フォルダを選ぶ」ダイアログは仕様上**フォルダしか一覧表示しない**（ファイルは選べないので表示されない）ため、1階層目のフォルダを開いても「icons」フォルダしか見えず、「ファイルが消えた」ように見えてしまったというわけでした。

### 直し方：ZIPの中身はフォルダで包まない

対策はシンプルで、**ZIPのアーカイブ直下にファイルを直接置く**ようにしました。

```bash
# NG: 中身をフォルダに包んでからzip化する
zip -r out.zip my-folder/

# OK: フォルダの中身を直接、アーカイブの直下に入れる
cd my-folder
zip -r ../out.zip .
```

こうすると、Windowsが自動生成する1つのフォルダの中に、`manifest.json`たちが直接入る状態になります。「展開してできたフォルダ＝そのまま選ぶフォルダ」になるので、二重に潜る必要がなくなりました。

## つまずき②：説明書のファイル名が文字化けした

1つ目を直して再配布したところ、今度は別の問題が発覚しました。日本語で書いた「はじめにお読みください.txt」という説明書ファイルが、展開後にこうなっていたのです。

```
繧ッ繧゗繝斉ヲ繝ォ縺輔■...txt
```

[スクショ挿入箇所：文字化けしたファイル名が並んだフォルダのスクリーンショット]

内容ではなく**ファイル名だけ**が化けるという、地味に厄介な現象でした。

### 原因：ZIPの中の日本語ファイル名は、環境によって解釈がズレることがある

ZIP形式は歴史的に、ファイル名の文字コードをどう扱うかが統一されていませんでした。作成する側（今回はLinux環境の`zip`コマンド）と、展開する側（Windowsの標準機能）とで、日本語のような非ASCII文字の解釈がズレると、正しいバイト列のはずが化けて表示されてしまいます。

内容そのものは無事なので実害は少ないのですが、初めてこのツールを触る相手からすると「なんか壊れてる」という第一印象を与えてしまい、地味に信頼を損ないます。

### 直し方：配布物のファイル名はASCII文字にする

一番確実だったのは、**そもそも日本語のファイル名を使わない**ことでした。

```
はじめにお読みください.txt   →   INSTALL_README.txt
```

ファイルの**中身**は日本語のままで問題ありません。文字化けが起きるのはあくまで「ファイル名」というメタ情報の部分だけなので、ファイル名だけをASCII文字にすれば、環境に関係なく安定して開けるようになります。

---

## まとめ

配布したZIPの中身自体は、最初から最後まで一度も壊れていませんでした。問題は全部、「渡す形式」の方にありました。

- **ZIPの中身をフォルダで包まない**（Windowsの自動フォルダ生成と衝突して二重入れ子になる）
- **配布物のファイル名はASCII文字にする**（日本語ファイル名は環境によって文字化けしうる）

どちらも、開発している自分の環境（Mac/Linux）ではまったく再現しない類のトラブルで、**実際に第三者に使ってもらって初めて発覚した**ものでした。自分のPCで動作確認をして「よし完成」と思った後こそ、一度誰かに渡してみる価値があると実感した出来事です。
