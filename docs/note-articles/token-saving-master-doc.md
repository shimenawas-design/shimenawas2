# 「開発に夢中になっていたらトークンが爆食いされた」件

Vibe Coding（AIに指示を出しながらアプリやコンテンツを作るスタイル）で、私は「茶丸」という音楽・コンテンツ量産プロジェクトを走らせていました。

話数ごとの企画、プレイリスト設計、AI作曲サービス（Suno）の選定ロジック、制作ルール……。こうした情報を一箇所にまとめておきたくて、`統合マスター.md`という1つのファイルに全部書き込んでいました。

最初は快適でした。AIに「`統合マスター.md`を見て」と伝えるだけで、プロジェクトの全体を把握してくれる。まさに万能ノートです。

ところが、話数が01話、02話……と増えていくたびに追記を重ねた結果、このファイルは**3,407行**まで膨れ上がっていました。

そして異変に気づきます。

- 「進捗をちょっと確認したい」だけなのに、妙に待たされる
- 気づけば1日の利用量上限にすぐ到達してしまう
- 話数がひとつ増えるだけの軽い更新のはずが、やたら重い

# なぜトークンが爆食いされていたのか？（原因の分析）

調べてわかったのは、Claude Codeの仕組み上、避けようのない性質でした。

## 原因1：`@ファイル名`は「全文読み込み」である

Claude Codeで`@統合マスター.md`のようにファイルを指定すると、AIはそのファイルの要約ではなく**全文**を読み込みます。3,407行ともなると、それだけで数万トークン単位の消費になります。

## 原因2：「軽く確認したいだけ」でも全文読み込みが発生する

「話数の進捗だけサッと教えて」という軽い質問でも、AIからすればファイル全体を読まない限り答えられません。**知りたい情報が数行でも、読まされる分量は3,407行**なのです。

## 原因3：更新頻度の違うものが同居していた

`統合マスター.md`の中身をよく見ると、

- 頻繁に更新される「話数ごとの進捗・要対応リスト」
- ほとんど更新されない「制作ルール（Suno選定ロジック・40Hz手順・量産マトリクスなど）」

が同じファイルの中に同居していました。話を1話分追記したいだけなのに、変わらないルール部分まで一緒に読み書きする羽目になっていたわけです。しかもファイルが大きいほど、**1回の編集ミスで全体の整合性が壊れるリスク**も上がります。

# 【基本編】AIに素直に頼んだら、一発で解決策が返ってきた

原因はわかった。でも、どう直せばいいのか——正直ここで悩む時間がもったいなかったので、私は自分で構成案を考えるのをやめて、**そのままAI（Claude）に相談すること**にしました。

投げたプロンプトはこれだけです。

> 「統合版マスターを常に読むとトークンの消費が半端ないので改善したい」

驚いたのは、この一言だけで、AI自身が「じゃあファイルの役割を分けましょう」と、具体的な設計を提案してくれたことです。分割の軸として提示されたのは次の3つでした。

| 軸 | 茶丸プロジェクトでの例 |
|---|---|
| **更新頻度**（よく変わる vs 安定） | 進捗・要対応リスト（頻繁）／制作ルール・付録（安定） |
| **粒度**（全体像 vs 個別詳細） | インデックス（全体像・要点）／話別ファイル（個別の詳細） |
| **時系列・カテゴリのまとまり** | 話数のかたまりごと（01-12話 / 13-25話 / 26-29話 / 30-38話）に分割 |

この軸に沿って、実際に組み直した構成がこちらです。

```
統合マスター_YYMMDD.md      ← 397行。共通ルール・要対応リスト・直近の進捗だけ。通常はこれだけ読む
chamaru_プレイリスト設計.md  ← 342行
chamaru_話別_01-12.md       ← 1,001行（話数ごとの詳細：タイトル・概要・タグ・プロンプト）
chamaru_話別_13-25.md       ← 1,125行
chamaru_話別_26-29.md       ← 441行
chamaru_話別_30-38.md       ← 875行
chamaru_制作ルール.md        ← 156行（付録：Suno選定ロジック・40Hz手順・量産マトリクスなど）
```

ポイントは、**「普段読むもの」と「たまにしか読まないもの」を物理的に別ファイルへ分けた**ことです。インデックス（397行）さえ読めば全体像とやることリストがつかめて、特定の話数の詳細が必要なときだけ該当する話別ファイルを個別に開く——という設計にしたことで、通常のセッションではインデックスだけで完結するようになりました。

### インデックスに残すもの／逃がすもの

分割する際に迷ったら、次の基準で仕分けています。

**インデックスに残すもの**
- ファイル構成の一覧表（どこに何があるか）とナビゲーション
- 全話・全案件共通のルール（頻繁に参照されるが短いもの）
- 要対応リスト（最も参照・更新頻度が高いので、あえてここに集約する）
- 直近の進捗ログ（最新の数件だけ。古いものは圧縮・要約して残す）

**topicファイルに逃がすもの**
- 個別の詳細（1件あたりの情報量が多く、同時に1件しか見ない類のもの）
- 安定した参照ルール・手順書（変更頻度が低い）
- 過去の記録・経緯（読み返す頻度が低い）

「自分で頑張って設計を考える」のではなく、「困っていることをそのままAIに伝える」——これが一番の近道でした。

# 【応用編】AIに"全部読ませずに"一瞬でファイルを分割するBashテクニック

さて、ここで新たな疑問にぶつかります。

「じゃあ、その3,407行のファイルを7つに分割する作業自体、AIに頼んだらまた全文読み込みが発生して、結局トークンを消費するのでは……？」

その通りです。ここからは少し技術的な話になりますが、**分割作業そのものでAIに全文を読ませない裏技**を紹介します。使うのはBash（ターミナルのコマンド）です。

## ステップ1：見出しと行番号だけを取得する

まず、ファイルの中身全部ではなく、**見出し（`#`や`##`）と、その行番号だけ**を一覧にします。

```bash
grep -n "^#\{1,2\} " 統合マスター.md
```

3,407行のファイルでも、見出しの数はせいぜい数十行。**AIに渡す情報量が劇的に少なくなる**のがポイントです。本文は一度もモデルの文脈に載りません。

## ステップ2：行番号から範囲を計算する

見出しの行番号がわかれば、「このセクションは何行目から何行目まで」という範囲が計算できます。

## ステップ3：`sed`で該当範囲だけを切り出す

範囲がわかったら、`sed`コマンドでその部分だけを新しいファイルに書き出します。

```bash
# 例：話別01-12のセクションを新しいファイルへ切り出す
sed -n '89,1089p' 統合マスター.md > chamaru_話別_01-12.md
```

これをセクションの数だけ繰り返せば、元のファイルを1行も欠かさずに、複数のファイルへ分割できます。

## ステップ4：`wc -l`で行数の整合性をチェックする

最後に、分割前後で行数がちゃんと一致しているか確認します。

```bash
wc -l 統合マスター.md chamaru_話別_01-12.md chamaru_話別_13-25.md chamaru_制作ルール.md
```

境界がずれて欠落があれば合計行数が減るので、すぐに気づけます。

## ステップ5：新しいインデックスだけは自分の手で書き直す

分割そのものはBashで完結しますが、新しい**インデックス（要約・ナビゲーション）**だけは、AIに内容を扱ってもらって書き直します。ここだけは「軽い情報を扱う」作業なので、コストは小さく済みます。

# 運用ルール（分割してからが本番）

分割して終わりではなく、運用時のルールも決めておくと効果が長持ちします。

- **通常はインデックスだけ読む。** 特定の話数・詳細が必要になった時だけ、該当するtopicファイルを開く
- **更新時も同様。** 更新箇所がどのファイルに属するか先に判断し、そのファイルだけ`Grep`→`Read`（範囲指定）→`Edit`する。全ファイルを読み直さない
- **索引の一覧表は古くなりがち。** 新しいtopicファイルを作ったら、必ずインデックスの一覧表も更新する
- **同じ内容を2箇所に書かない。** インデックスとtopicファイルで情報が重複すると、更新時に片方だけ直して不整合になる。インデックス側は「要約・リンク」に徹する

逆に、**すべてのファイルを分割すればいいわけではありません。** 目安として、

- 1回の読み込みで数万トークンを超える（だいたい1,000〜1,500行以上）
- 「今回の用件では読む必要のない部分」が半分以上ある
- 更新頻度が明らかに違う内容が同居している

に当てはまらない小〜中規模のファイルは、無理に分割しないほうがコスパが良いです。分割自体もファイル数が増えて参照が複雑になるコストがあるので、**肥大化して実際に困ってから分割する**くらいで十分です。

# まとめ＆驚異のビフォーアフター

茶丸プロジェクトでの実績です。

| 状態 | 行数 |
|---|---|
| 分割前 | `統合マスター.md` 3,407行（単一ファイル） |
| 分割後（通常読むもの） | インデックス **397行** |
| 分割後（詳細・必要な時だけ開く） | `chamaru_プレイリスト設計.md`(342行)／`chamaru_話別_01-12.md`(1,001行)／`chamaru_話別_13-25.md`(1,125行)／`chamaru_話別_26-29.md`(441行)／`chamaru_話別_30-38.md`(875行)／`chamaru_制作ルール.md`(156行) |

**通常の状況確認・進捗更新は、397行のインデックスだけで完結するようになりました。3,407行 → 397行で、典型的な参照コストは約9割減。**

[スクショ挿入箇所：分割前後で「読む行数」を比較した図]

やったことは、たった2つです。

1. AIに「困っている」とそのまま相談し、**更新頻度・粒度・時系列でファイルを分ける設計**をもらった
2. ファイル分割の作業自体は、**Bash（grep・sed・wc）でAIに全文を読ませずに**実行した

「AIにたくさん読ませれば賢く動いてくれる」は誤解で、むしろ**AIに何を読ませないかを設計すること**が、快適なVibe Coding環境をつくる一番の近道だと痛感した出来事でした。
