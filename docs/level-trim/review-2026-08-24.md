## 🔴 1. Warm Cache のカット位置に安全余裕がない

**事実関係**
- take2 のハミングは **6:00以降**（4.3・ユーザーが実際に聴いて特定）
- 最終構成は take2 を **3:00〜6:00** で使用（4.5）

**問題**：カット位置がハミング開始点とちょうど一致している。この6:00は耳で聴いて特定した時刻であり、秒単位の精度はない。実際の開始が5:57なら、末尾3秒に残る。

**対処**：末尾を **5:45前後まで詰め、そこから3〜5秒のフェードアウト**をかける。曲は `no climax` / `Outro - slow fade` で終わる設計なので、15秒短くなっても失うものはない。

```bash
ffmpeg -i "02 Warm Cache (combined).wav" -t 345 \
  -af "afade=t=out:st=340:d=5" -map_metadata -1 \
  "02 Warm Cache (final).wav"
```

## 🔴 2. 音量で選ぶ基準が、この曲群の設計方針と逆を向いている

4.2 は「音量差が明確な区間だけ**密度が高い方**を採用」としている。しかしシリーズ共通のDNAは：

> `understated and non-intrusive` / `no build-up` / `no climax` / `sustained and unchanging`

**「密度が高い＝良い」という前提が設計思想と矛盾している。** 作業用BGMとして望ましいのは、むしろ変化が少なく目立たない区間。

さらに 4.2 自身が「密度だけでは良い区間を判断できない」と認めており、Long Poll と Hot Path では機能せず単体採用に落ちている。**6曲中3曲が、同じ文書が機能しないと述べている基準で組まれている。**

**対処**：耳で確認するしかない。試聴時に「後半のほうが賑やかになっていないか」を意識して聴く。賑やかになっていたら、選択を反転させた版を作り直す価値がある。

## 🔴 3. バイト比較は「音楽的に妥当か」を検証していない

4.4 の手法は**ファイルの取り回しが意図通りか**を確認するもので、それ自体は正しく機能している。ただし文書の書きぶり（「意図通りの音源が使われていることを確認済み」）は、音楽的な妥当性まで検証されたかのように読める。

**未検証のリスク**：Sunoの2テイクは、同じプロンプトから生成されていても**互いに独立**であり、テンポも位相もキーも揃っている保証がない。3秒のクロスフェードは2つの音を実際に重ねるため、重なった区間で**キーの衝突やテンポのにじみ**が起きうる。

4.3の問題1「テンポ・音量が急変する」は、まさにその兆候。`acrossfade` への変更で**継ぎ目は滑らかになるが、根本原因（2テイクが別物であること）は解決していない**。

**最優先の試聴対象は Thread Pool**（クロスフェード3回／4:31）。継ぎ目の密度が最も高い。

## 🟡 5. 44.1kHz変換はリサンプラーを明示する

48000 → 44100 は整数比でないため、リサンプリング品質が効く。デフォルトより soxr を明示するほうが安全。

```bash
ffmpeg -i "in.wav" -af "aresample=resampler=soxr:precision=28" \
  -ar 44100 -map_metadata -1 "out.flac"
```

WAV → FLAC は可逆なのでこの経路が最善（**MP3を経由しないこと**）。
